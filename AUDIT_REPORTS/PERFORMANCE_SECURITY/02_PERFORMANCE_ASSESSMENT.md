# Performance Assessment

## Summary

The engine has strong implementation-level performance features: parallel segments, dynamic splitting, adaptive reductions/retirement based on learned host limits, per-download and global speed limiters, HTTP connection pooling, FTP session reuse, streaming, positional writes, slow-connection shedding, sparse files on supported filesystems, and bounded resume/checksum blocking work. These are source-verified capabilities, not all independently measured in this audit.

## CPU and Async Runtime

- The desktop app creates Tokio's default multi-thread runtime with `Runtime::new()`; no explicit worker count is set ([main.rs:314](../../crates/app/src/main.rs#L314)). The CLI and headless paths also create standard Tokio runtimes ([cli/src/lib.rs:420](../../crates/cli/src/lib.rs#L420), [headless.rs:94](../../crates/app/src/headless.rs#L94)).
- Network reads and waits are asynchronous. Positional file reads/writes, checksum hashing, disk-space probes and state-file persistence are moved to `spawn_blocking` at the main I/O boundaries ([download.rs:2115](../../crates/engine/src/download.rs#L2115), [download.rs:3284](../../crates/engine/src/download.rs#L3284), [disk.rs:37](../../crates/engine/src/disk.rs#L37)).
- Each successful batch write schedules a blocking-pool job. With many simultaneous downloads this can queue many jobs; there is no engine-wide blocking-I/O semaphore around writes. This is a scaling concern, not proof of starvation.
- Planner and snapshot operations use mutex-protected shared state. Per-download work is serialized briefly through planner and view locks; no source evidence establishes problematic contention at normal worker counts.
- Checksum tasks are globally limited to two via a static semaphore ([download.rs:2102](../../crates/engine/src/download.rs#L2102)).

## Memory

- Every worker maintains a `Vec` initially allocated for 256 KiB; network chunks are copied into it and written once they reach the threshold, a segment end, or a one-second flush deadline ([download.rs:3096](../../crates/engine/src/download.rs#L3096), [download.rs:3211](../../crates/engine/src/download.rs#L3211)).
- During a slow `sync_data`, the engine intentionally buffers received bytes. `FLUSH_HOLD_MAX` is 256 MiB per download, divided by configured worker count, not a process-wide memory budget ([download.rs:46](../../crates/engine/src/download.rs#L46), [download.rs:3243](../../crates/engine/src/download.rs#L3243)).
- Each `Download` also stores bounded event history of 50 entries; planner segments are proportional to split count. The local queue and active-download count are not globally capped by this engine code.
- `ResumeState::load` reads the whole JSON file before deserialization, and its segment list has no explicit count/size limit ([state.rs:70-L81](../../crates/engine/src/state.rs#L70-L81)). This matters mainly for untrusted or corrupted sidecars.
- Streaming keeps ordinary HTTP body memory proportional to active workers rather than file size. Unknown-size downloads use a single stream. No leak was demonstrated by source inspection.

## Disk I/O

- HTTP workers use OS positional `write_at`/`seek_write`, avoiding shared seek-cursor races during random segment writes ([download.rs:3367](../../crates/engine/src/download.rs#L3367)).
- Batches are not individually synchronized. Resume metadata synchronization uses `part.sync_data()` before writing an atomic state file. Save checks run each configured tick (default two seconds), but actual flush waits for at least 1 MiB to 64 MiB progress or 30 seconds and backs off according to previous flush latency, capped at 60 seconds ([download.rs:2176](../../crates/engine/src/download.rs#L2176), [download.rs:2248](../../crates/engine/src/download.rs#L2248)).
- This deliberately trades recovery work for reduced stalls: source comments state that a slow disk may lose up to 60 seconds of progress (estimated there as about 7 GB at 1 Gbit/s). Saved offsets still follow synced data. The estimate is a design bound, not a benchmark from this audit.
- Completion sets the final length, disables sparse mode where applicable, calls `sync_all`, then renames the part file and removes state ([download.rs:2127](../../crates/engine/src/download.rs#L2127)). Parent-directory sync and power-loss durability of the atomic JSON helper were not inspected.
- The disk preflight adds a 128 MiB free-space margin and recognizes FAT32's max file size; it is best effort, not a reservation against competing writers ([disk.rs:11](../../crates/engine/src/disk.rs#L11)).

## Network Efficiency and Bottlenecks

- DNS can be system, plain DNS-over-TCP, DoT or DoH; custom multi-address resolution races connections and remembers a winner. DNS cache lifetime and per-download resolver reuse should be measured before tuning ([dns.rs:1](../../crates/engine/src/dns.rs#L1)).
- HTTP is explicitly HTTP/1.1. TLS handshakes can benefit from pooled keep-alive sockets within one download, but there is no cross-download shared reqwest client. No HTTP/2 multiplexing or HTTP/3 is configured.
- Small files use `ceil(size / 64 KiB)` to cap initial workers, but later splits and scheduling still generate more requests. Historical run 5 reported 31 requests for a 1 GiB fast-link case versus 9 for the compared client and 24 versus 8 under latency; the small 256 KiB case used 6 versus 4. This is a potential request/connection overhead tuning area, not proof it is universally slower ([run5/REPORT.md](../../docs/bench/run5/REPORT.md)).
- No global admission controller bounds concurrent downloads or their aggregate connection/memory use. Queue scheduling caps files per queue, but multiple queues and manually added downloads can multiply this ([queue.rs:155](../../crates/app/src/queue.rs#L155)).
- FTP does not use the HTTP proxy; this is explicitly documented in the FTP source. Its direct control/data connections do honor the selected adapter route ([ftp.rs:20](../../crates/engine/src/ftp.rs#L20)).

## Prioritized Performance Weaknesses

- **PERF-001 (P1 in high-concurrency use):** per-download, not global, memory, connection and blocking-write budgets; concurrent downloads can multiply resource use. See [PERF-001](06_FINDINGS_AND_RISKS.md#perf-001-memory-and-blocking-writes-are-not-globally-admitted) and [ROAD-003](07_IMPROVEMENT_ROADMAP.md#road-003-global-resource-admission).
- **PERF-002 (P2):** potential request overhead for small/fast downloads and high latency; historical benchmark snapshots motivate a current controlled benchmark, not an immediate algorithm replacement.
- **PERF-003 (P2):** the sync policy trades recovery point for disk throughput; this is a design trade-off, not a demonstrated issue on this audit host.
- **PERF-004 (P3):** HTTP/2/3 are intentionally absent; evaluate only if multiplexing can preserve worker connection semantics. No improvement is claimed without measurement.
- **REL-002 (P2):** response-end metadata (`Content-Range` end) is parsed but ignored; malformed ranges may lead to retries or ambiguous validation. No corruption was reproduced. See [REL-002](06_FINDINGS_AND_RISKS.md#rel-002-content-range-end-is-not-validated).

## Measurement Boundary

No benchmark was run for this audit. `docs/bench/run5/REPORT.md` is a historical Windows 11 / i5-13400F local-lab report dated 2026-10-29, not measurements at the audited revision. It reports MDM working-set peaks around 96-106 MiB in several scenarios, but methodology and raw records belong to that run. See [Testing and Benchmark Plan](08_TESTING_AND_BENCHMARK_PLAN.md).
