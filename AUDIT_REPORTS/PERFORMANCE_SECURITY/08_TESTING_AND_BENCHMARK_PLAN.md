# Testing and Benchmark Plan

## Existing Coverage Located

The source tree contains engine unit and integration tests plus a lab server. Static annotation count across engine, app and labserver sources during this review was 557 `#[test]` / `#[tokio::test]` occurrences; this count is not a test execution result and may include test modules not relevant to downloads.

## Coverage Gaps to Close

1. **Filesystem:** pre-existing `.mdm.part` symlink in `Destination::File`; symlink swap between validation/open; concurrent destination creation immediately before final rename; permissions on part/state files; resume from symlinked part.
2. **SSRF and redirects:** public-to-private and private-to-public redirect chains; DNS rebinding; IPv4-mapped IPv6; loopback, link-local and metadata-service test fixtures; document allowed local/LAN use cases and caller trust.
3. **Credentials:** HTTP URL user-info and secret query values in state file; cross-host/port/scheme redirects for Cookie/Authorization/Proxy-Authorization; HTTP→HTTPS and HTTPS→HTTP; 307/308 POST body forwarding; verify no secrets in errors/events/crash output.
4. **HTTP range validation:** Content-Range missing, invalid unit, reversed endpoints, mismatched start/end/total, wildcard total, 416, false Content-Length, too-short/too-long response, encoded response, changed validators, late 200, and clean retry/no false completion.
5. **FTP data channels:** malicious PASV target, EPSV, server behind NAT, TLS data protection, route binding, FTP credential redaction and plaintext-mode warnings; inspect suppaftp's exact locked source before test assertions.
6. **Resource limits:** oversized resume JSON, huge segment vector, many downloads x 32/128 workers, many simultaneous blocking writes, slow disk flush, unlimited-speed and low-speed cancellation, very large/unknown-length response and disk-full races.
7. **Reliability:** crash between each state sync/atomic write, final sync/rename/state removal; same-size destination replacement; corrupted part bytes with and without validators/checksum; cancel during network, limiter wait, disk write and state save.

## Security Test Method

- Use only `mdm-labserver`, temporary directories and reserved test-only IP fixtures; never point the test at real metadata services or user data.
- Make the test oracle byte-level: verify untouched sentinel files, exact final file bytes/length, state contents, expected errors and absence of unexpected requests.
- Separate policy tests from implementation tests. In particular, SSRF policy must first specify whether local/LAN downloads are allowed and which caller classes are trusted.
- Run filesystem race tests per supported OS because `rename`, symlink and no-replace semantics differ.
- Fuzz pure parsers (`Content-Range`, filename headers, resume JSON validation) with explicit resource limits. Fuzzing itself should be approved and run in a sandbox.

## Performance Benchmark Method

The checked-in harness is Windows-oriented: it uses Win32 APIs and an installed IDM path, runs clients alternately, discards one warm-up, and records end-to-end/network time, connections, requests, bytes, CPU and peak working set ([bench.py](../../tools/bench/bench.py)). The historical report is from Windows 11, an i5-13400F, local labserver and defaults of eight connections ([run5/REPORT.md](../../docs/bench/run5/REPORT.md)). It is not a current audit measurement.

For a reproducible current baseline:

1. Pin commit, toolchain, OS/kernel, CPU, filesystem, power mode and labserver revision; capture clean environment metadata.
2. Run repeated randomized/alternating trials with warm-up and enough samples to report median, IQR and confidence intervals. Separate startup, transfer and finish phases.
3. Test: fast local 1 GiB; capped throughput; high RTT; loss/drop/retry; server max connections; slow worker; 256 KiB small file; multi-download contention; slow disk/flush; checksums; HTTP and FTP.
4. Measure throughput, wall time, CPU time, peak RSS, bytes transferred versus file size, HTTP request count, sockets/connections/TLS handshakes, retries, disk bytes written, sync latency, time blocked in writes and cancellation latency.
5. Compare variants on identical hardware/data with no concurrent benchmark jobs; publish raw samples and exact command/configuration. Do not infer cross-platform performance from a Windows-only run.

## Proposed Acceptance Criteria

These are targets for future test design, not current results:

- Correctness: zero byte mismatches and zero overwrite of sentinel/final target in all injected failure and race scenarios.
- Range validation: all malformed/inconsistent range cases fail or retry without marking a corrupt/partial file complete.
- Resume: after simulated restart, saved bytes are either validated by strong validators/checksum or re-fetched; no state claims unsynchronized bytes.
- Resource bounds: under the agreed maximum active downloads/workers, peak RSS and blocking queue depth remain within explicit budgets; cancellation of queued/rate-limited work returns promptly.
- Security: secrets are absent from serialized state and logs under dummy credentials; redirect credentials follow the documented same-origin/site policy only.
- Performance: no optimization is accepted unless repeated runs show a statistically supported improvement without regression in correctness, resource caps or low-speed/high-latency scenarios.

## Safe Execution Boundary

Build/test/benchmark runs may create `target/`, update Cargo caches, or start local servers. They were not run for this audit. Dependency advisory checks may access external feeds or mutate local caches, so authorization is needed before those checks.
